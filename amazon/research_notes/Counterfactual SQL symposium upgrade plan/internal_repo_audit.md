# Internal repo audit: gaps, loose ends, quick wins and inconsistencies for the Amazon Trusted AI Symposium 2027 paper

Scope: the repo at `~/developer/comps/sexsi_hack` only, read-only, as of 2026-11-21 (HEAD `5df6f17`, "Amazon symposium: paper draft iteration 0"). Sources are repo-relative paths. Public pages were read through the HF and GitHub JSON APIs. Numbers marked **[recomputed]** come from my own read-only CPU pass over files in the repo. That script lives in the session scratchpad, not in the repo, so these numbers must be re-derived by a committed script before the paper uses them.

## 1. What exists: experiments, artifacts, code quality, tests

### Takeaway
The project already has a full, reproducible evidence base: 14 experiment families, all regenerated by `verify_all.py`, a 4-page iteration-0 draft whose 41 auto-checked numbers all match `results/`, 9 passing CPU tests and public HF and GitHub artifacts. The weak spots are not missing experiments but stranded or unreleased material: the seed-1 adapters, the curriculum and Spider trajectories, and intermediate checkpoints.

### Cited Findings
- **Experiments done**, each with a results file:
  - E0 reward audit, E1 blind rate vs DB size, E0-AgentTune exploit, A2/E6 Spider lucky passes of 8 published systems, A3/E7 SkyRL audit, A4/E8 voting and shaky flag, A1 training-reward replay;
  - E2 SFT, E3/E4 GRPO B vs C, E5 Command A cost and ROI, E10 DPO, E11 partial credit, E12 period-edge copies, E13 Spider transfer, E14 curriculum;
  - D1–D4 distillation (negative, removed from the article), leak check, manual audit of 48 trajectories.
  - Source: [amazon/PROJECT_REPORT.md §5](../../PROJECT_REPORT.md); [results/](../../../results).
- `runs/verify_all.log` ends "OK: every results/*.json reproduced exactly" — [PROJECT_REPORT §5 "verify_all"](../../PROJECT_REPORT.md).
- **Tests.** `tests/test_rewards.py` and `tests/test_agenttune_reward.py` give 9 passed in 37 s on the CPU venv (run read-only with `-p no:cacheprovider`). `test_precision.py` and `test_logit_distil.py` need torch, which is not in `.venv`. Sources: my run of `.venv/bin/python -m pytest`; [reports/Strengthening results Nov 9.md §4](../../../reports/Strengthening%20results%20Nov%209.md).
- **Paper tooling.**
  - `amazon/paper/iteration0/build.sh` runs `make_tables.py` (Tables 1, 2 and two appendix tables are generated from JSON, not typed) and then `check_numbers.py`. It reports "41/41 numbers match".
  - The PDF has 8 pages. The body ends on page 4 and Acknowledgments start page 5. There are 3 overfull hboxes (0.8–2.7 pt).
  - Sources: [build.sh](../../paper/iteration0/build.sh); [build.log](../../paper/iteration0/build.log); [notes/claim_source_map.md](../../paper/iteration0/notes/claim_source_map.md).
- **Code size.** About 5.2k lines of Python: core `sqlcf/` (cf.py 440, templates.py 374, audit.py 238, db.py 202, rewards.py 105, compare.py 100), `train.py` 175, `evaluate.py` 225, plus about 40 scripts. Source: `wc -l` over the repo.
- **GRPO reward logs** exist for all 4 trained arms, 1440 rollouts each. Each line holds the full per-DB pass vector (`checks`) and the SQL, but no item id. Files: `runs/grpo_B_rewards.jsonl`, `runs/grpo_C_rewards.jsonl`, `runs/grpo_B_cur_rewards.jsonl`, `runs/grpo_Cmin_cur_rewards.jsonl`.
- **No intermediate GRPO checkpoints locally.** `find runs -name 'checkpoint-*'` finds only `runs/sft/` and `runs/sft_distil/`. `train.py` GRPO uses `save_steps=20` ([train.py](../../../train.py) L131), so step-20/40 checkpoints may once have existed on the VM. Not verified.
- **Seed 1.** The seed-1 adapters (B_s1, C_s1) exist only on the stopped `sqlcf-l4` disk. B_s1 finished 60/60. C_s1 is only presumed finished. Sources: [PROJECT_REPORT §5 "Seed 1"](../../PROJECT_REPORT.md); [progress.md, Nov 16 tail](../../../progress.md).
- **Seed 1 varies only the prompt order.** `scripts/vm_seed1.sh` notes that `--seed` changes the prompt order and the torch RNG, but "TRL fixes the colocated vLLM engine seed to the process index, so seed 0 and seed 1 differ through the prompt order". Source: [scripts/vm_seed1.sh](../../../scripts/vm_seed1.sh) header.

### Inferences
- The evidence base needs no new GPU runs to fill a 4-page paper. Upgrades should go to robustness (seeds, held-out family, real-benchmark copies) and presentation (monitor curve, schematic), not to more training variants.
- If seed 1 is evaluated, the paper should say what "seed" means here: prompt order plus torch RNG, not the vLLM sampling seed. Otherwise a reviewer may over-read two seeds as independent runs.

### Gaps
- Whether C_s1 actually completed, and whether GRPO checkpoint-20/40 directories survive on the VM disk, cannot be checked without starting the VM (out of scope).

## 3. Which CPU-only re-analyses could we add immediately?

### Takeaway
At least five analyses need no GPU and no new data:
1. the per-family audit, already in `e0_reward_audit.json` but unused;
2. the advantage-sign-flip and signal-group replay from the reward logs;
3. the R̃−R "monitor" gap curves per step, which show a clear divergence in the curriculum pair;
4. an "effective copies" analysis showing that most training copies killed no mutant;
5. re-scoring stored trajectories for per-family lucky rates.

A genuine held-out-family audit and a family-blind-copy audit need a small code change plus a CPU rebuild of about a minute.

### Cited Findings
**(a) Per-family audit is already computed.** `results/e0_reward_audit.json` has 24 rows per family F1–F4. With blind copies (`R_cf_strict@random`, identical to mean@random at full pay), mutants paid by family are **[recomputed]**:

| Family | Blind CF | Single-DB R_exec_rex |
|---|---|---|
| F1 | 8.5% [6.5, 11.2] (n 551) | 22.1% |
| F2 | 20.2% [15.3, 26.2] (n 208) | 30.3% |
| F3 | 23.3% [20.1, 26.9] (n 579) | 36.3% |
| F4 | 17.0% [13.9, 20.7] (n 476) | 29.4% |

- Hacks paid under blind CF: F1 4.1%, F2 0%, F3 0%, F4 2.0%. Under the single-DB reward: 50–59%.
- Greedy (informed) CF mutant pay: F1 1.1%, F2 3.4%, F3 0.5%, F4 2.3%.
- Source: [results/e0_reward_audit.json](../../../results/e0_reward_audit.json) rows with `family != ALL`.
- **Caveat:** F4 is *not* held out in the audit. Its blind copies include F4-targeted edits: `later_tier` in 110 of 369 F4 items, `adjustments` in 65, `superseded_tier` in 51 **[recomputed** from `data/audit/items.jsonl` `dbs_random`**]**. So the 17.0% is not a held-out-family number.

**(b) Advantage replay over the logs** **[recomputed]**. Assumption: consecutive blocks of 6 lines form one GRPO group, matching `--G 6`. All 240 blocks per run have a constant `checks` length, which is consistent with but does not prove this. Advantages are std-normalised. The table counts rollouts whose advantage sign differs from B's:

| Run | Groups with nonzero reward variance | Sign differs from B: C-mean / C-strict / C-penalty(−0.5) |
|---|---|---|
| grpo_B | B 27/240, C-mean 33, C-strict 25, C-pen 31 | 52 / 76 / 80 of 1440 |
| grpo_C | B 26, C-mean 28, C-strict 22, C-pen 27 | 25 / 50 / 52 |
| grpo_B_cur | B 53, C-mean 105, C-strict 82, C-pen 107 | 374 / 515 / 524 |
| grpo_Cmin_cur | B 105, C-strict 33 | strict 477 / pen 482 |

- Lucky rollouts: 102 (B), 104 (C), 908 (B_cur), 680 (Cmin_cur). The first two match the A1 replay in [PROJECT_REPORT §5 E3](../../PROJECT_REPORT.md).
- In the main runs only about 11% of groups (27/240) carried any gradient under B. The rewards would have changed the advantage sign on only 3.6–5.6% of rollouts.
- In the curriculum, C-penalty or C-mean would have revived about twice as many groups as B (105–107 vs 53).
- The G1 gate figure ("8/40 groups with signal" on 240 SFT rollouts) is consistent with this low-signal picture. Source: [PROJECT_REPORT §3.4](../../PROJECT_REPORT.md).

**(c) R̃−R monitor curve.** This is the per-step share of rollouts that pass D0 and fail some copy, out of 24 rollouts per step **[recomputed]**:
- B: 0.104 (first 10 steps) → 0.075 (last 10)
- C: 0.133 → 0.058
- **B_cur: 0.588 → 0.729** (rising)
- Cmin_cur: 0.529 → 0.533 (flat)

The paper's discussion recommends "monitoring the R̃–R gap" ([main.tex](../../paper/iteration0/main.tex) §5) but shows no such curve. PROJECT_REPORT §7 item 5 already proposes this figure from the same logs.

**(d) Effective training copies** **[recomputed;** approximate, uses unordered multiset compare**]**.
- On the 445 GRPO prompts, 442 have only 2 copies and 3 have 3 (k_max = 3 is rarely reached).
- Of 893 chosen copies, only 202 kill at least one base-blind mutant.
- Per edit, the counts are (copies chosen, of which kill ≥1 mutant):

| Edit | Chosen | Kill ≥1 mutant |
|---|---|---|
| later_tier | 49 | 0 |
| superseded_tier | 52 | 0 |
| drop_customers | 93 | 0 |
| new_customers | 206 | 84 |
| cancelled_orders | 83 | 31 |
| dup_order | 118 | 29 |
| refunds | 83 | 26 |
| split_items | 56 | 13 |
| adjustments | 56 | 8 |
| zero_order_customers | 51 | 8 |
| split_payments | 46 | 3 |

- Only 178/445 GRPO items have any base-blind mutant.
- Tier copies on F1–F3 questions are trivially answer-preserving. `_select` in [sqlcf/cf.py](../../../sqlcf/cf.py) L413–428 fills the "preserving" slot with the best preserving copy *even when it kills nothing* (random tie-break). Such copies cannot make C differ from B.
- This is a concrete, code-level reason the training reward was weak, separate from "easy prompts". It also qualifies the claim that F4 is "never in any training reward": F4-targeted edits do appear in the training copies, but only as no-ops for F1–F3 questions.

**(e) Per-family lucky rates on the test set.**
- `results/e4_eval.json` stores only `verified_by_family` per model, not single-DB or lucky by family. `evaluate.py score` computes per-trajectory `single` and `verified` ([evaluate.py](../../../evaluate.py) L109–115, L160), so adding `single_by_family` is a one-line change, followed by a CPU re-score of the stored `results/traj_*.jsonl`.
- **Blind vs informed breakdown:** both are already in E0 (Table 1 rows). The test set has no informed/blind distinction: all 4 `TEST_OPS` copies grade every item ([sqlcf/cf.py](../../../sqlcf/cf.py) L381–383).

**(f) Test-copy strength by family** **[recomputed** from `data/test/items.jsonl`**]**. Base-blind mutants caught by the 4 family-blind test copies, as caught/blind:
- F1: 4/11
- F2: 4/4
- F3: 10/17
- F4: 36/71

The total of 54/103 matches [plan.md status](../../../plan.md).

**(g) Family-blind copies as a "schema-generic" audit.** `TEST_OPS` (resample, clone, flip_status, relabel_tier) are family-blind generic mutations ([sqlcf/cf.py](../../../sqlcf/cf.py) L270–318). Running the E0 candidate pool on audit bases with `TEST_OPS` copies would answer reviewer weakness #3 ("how does the method do on bugs nobody thought of"; [notes/self_review.md](../../paper/iteration0/notes/self_review.md)).
- Today the only family-blind evidence is the test copies' 54/103 catch rate.
- The change needed: give `EvalBase` a parent at size S's M-parent, or apply the ops to `Base.rows`; see Q4.

**(h) Held-out-family audit (proper).**
- Build the F4 audit items with a pool that excludes F4-targeted edits (`later_tier`, `superseded_tier`, `adjustments`), then report blind-CF F4 mutant pay.
- This needs a CPU rebuild, because `build_items` deletes unreferenced pool DBs ([sqlcf/cf.py](../../../sqlcf/cf.py) L402–405).
- Build time for the full audit was minutes. Source: [PROJECT_REPORT §3.7](../../PROJECT_REPORT.md) ("Data, copies, reward audit … CPU, minutes").

**(i) Spider-side CPU analyses on existing data.**
- `external/testsuite_db` (Zhong suites) and `external/ESMp` (gold plus 8 systems' predictions) are on disk.
- Possible additions:
  - mutate Spider-dev gold SQL with generic operators (drop DISTINCT, INNER↔LEFT, drop a WHERE conjunct, COUNT(*)↔COUNT(DISTINCT)) and audit single-DB vs suite pay rates;
  - score the stored `results/spider_*.jsonl` per question type.

  Both reuse `scripts/a2_spider_lucky.py`'s scorer. Sources: [scripts/spider_eval.py](../../../scripts/spider_eval.py) L1–11; `ls external/`.

### Inferences
- **Highest value per hour:**
  1. the monitor-gap figure for the curriculum pair: B_cur's lucky share rises while Cmin_cur's stays flat, the only training-time divergence evidence;
  2. the effective-copies finding: about 77% of training copies were inert, a mechanism for the null and an obvious fix (drop zero-kill copies, or use strict or penalty forms);
  3. the per-family audit table.

  All are under an hour of CPU scripting.
- The sign-flip replay turns the "7% disagreement" sentence into a sharper quantitative statement: "only 11% of GRPO groups carried any gradient; the CF reward changed the advantage sign of 3.6% of rollouts".
- A family-blind (TEST_OPS) audit plus a held-out-F4 audit would directly address self-review weaknesses #2 and #3 at zero GPU cost.

### Gaps
- The grouping-by-6 assumption for the reward logs has not been verified against TRL's sampler ordering. The logs carry no item id, so the exact mapping to prompts cannot be confirmed from logs alone.
- The effective-copies count uses an unordered comparison, so it is slightly off for the `ordered` templates (F3_top_customers). Re-run with `sqlcf.compare.match` for an exact figure.

## 4. How generic is sqlcf/cf.py, and what code changes are needed for real-benchmark copies or new rewards?

### Takeaway
The reward and grading layer is already schema-agnostic. `sqlcf/rewards.py` and `sqlcf/compare.py` need only items with `dbs`, `gold` and `ordered`. The copy generator `sqlcf/cf.py` and the generator `sqlcf/db.py` are hard-wired to the 8-table retail schema through positional tuple indices, table names, vocabularies and domain helpers.

Porting to a second synthetic domain means rewriting `db.py`, `templates.py` and the edit functions. That takes days and is "a second instance", not a port. Porting to Spider or BIRD is easier if Zhong's test-suite DBs (Spider dev) serve as the copies. True per-question copies for arbitrary schemas need a new, generic operator module driven by sqlglot or the schema.

### Cited Findings
**Schema-agnostic parts.**
- `rewards.py` computes per-DB pass vectors from `dbs` (paths relative to `SQLCF_DATA`), `gold` and `ordered`, and combines them: `R_exec_rex = v[0]`; `R_cf_mean`; `R_cf_strict`; `R_cf_soft`. It logs every rollout to `SQLCF_REWARD_LOG`.
- Adding a new reward form is one line in `_make(...)`, e.g. a lucky-pass penalty `lambda v: -0.5 if v[0] and not all(v[1:]) else float(v[0])`.
- Sources: [sqlcf/rewards.py](../../../sqlcf/rewards.py) L52–96; `compare.run`/`match` are generic SQLite ([sqlcf/compare.py](../../../sqlcf/compare.py)).

**Hard-coded in cf.py.**
- Positional row access throughout:
  - `_f_customers` uses `c[2]` = city;
  - `_f_orders` uses `o[1]` customer, `o[2][:4]` year, `o[3]` status;
  - `_tiers_by_customer` uses `r[3]` = valid_from;
  - `e_split_items` uses `i[3]` qty, `i[2]` product.
- `FOCUS_KEYS = ("city","year","category")`.
- Every `e_*` edit calls retail helpers: `db.add_order`, `db.add_customer`, `db.next_ids`, `db.TIERS`, `db.END`.
- `_closure` hard-codes the FK tree customers→orders→{order_items, payments, refunds, invoice_adjustments}.
- `EvalBase` hard-codes a size-M parent and `TEST_N = 50`.
- Source: [sqlcf/cf.py](../../../sqlcf/cf.py) L31–217, L270–337.

**Hard-coded elsewhere.**
- `db.py`: `SCHEMA`, `TABLES`, `CITIES`, `CATEGORIES`, `TIERS`, `YEARS`, `GLOSSARY` and business-rule assertions `_RULES` ([sqlcf/db.py](../../../sqlcf/db.py) L12–48, L164–188).
- `templates.py`: 18 templates, each with a pandas re-implementation, so gold validation needs per-template pandas code ([sqlcf/templates.py](../../../sqlcf/templates.py)).
- `agent.py`: `_DB_ID = ^[SML]_s\d+$`, and the system prompt embeds the retail `SCHEMA`/`GLOSSARY` ([sqlcf/agent.py](../../../sqlcf/agent.py) L11–34). The Spider path already has its own `run_sql` and schema prompt ([scripts/spider_eval.py](../../../scripts/spider_eval.py) L57–86).

**Generic parts of item building.**
- `build_items` drives everything through `t.grid()`, `t.sql`, `t.paraphrases`, `t.mutants`, `t.pandas` and `B.pool(focus)` ([sqlcf/cf.py](../../../sqlcf/cf.py) L340–410).
- The selection logic `_select` and the item checks (degenerate, shuffled determinism, preserving/changing classification) are schema-independent and reusable.

**Training and eval are already item-driven.**
- `train.py --items PATH --reward NAME` builds GRPO rows via `dataset_row(item)`. Any items file with `question`, `dbs`, `gold`, `ordered` trains ([train.py](../../../train.py) L62–64, L160–168).
- `evaluate.py grade()` uses `checks(sql, item["dbs"], item["gold"], item["ordered"])` ([evaluate.py](../../../evaluate.py) L109–115).
- A Spider items file in this format would therefore plug into GRPO and eval. The only changes are the tool/DB-id routing (`agent.run_sql`/`db_path`) and the system prompt.

**What the repo's own plans say a port needs.**
- PROJECT_REPORT §10 table: "Generate copies for Spider and BIRD training databases … Our copy generator knows one schema" — forecast only, not built. Source: [PROJECT_REPORT §6, "§10 With more compute"](../../PROJECT_REPORT.md).
- The Nov 9 report proposes the operators for "schema-only copies": "duplicate and delete rows, inject NULLs, create ties on ORDER BY/LIMIT columns, and shift values across WHERE thresholds". Source: [reports/Stronger counterfactual SQL entry.md](../../../reports/Stronger%20counterfactual%20SQL%20entry.md), self-consistency section.
- cheap_extensions #6 estimates 4–6 h for BIRD generic operators, "Medium but risky". Source: [cheap_extensions.md](../../../research_notes/Stronger%20counterfactual%20SQL%20entry/cheap_extensions.md).

### Inferences
**Minimal path to real-benchmark copies, in order of cost:**
1. **Spider dev with Zhong suites as copies** (0 new generator code). Write a small builder that emits items `{question, gold_sql, dbs: [orig, suite_1..K], gold: [...], ordered}` from `external/ESMp/spider_dev/gold.txt` and `external/testsuite_db`. Run `sqlcf.audit e0`-style scoring with generic SQL mutants to get a real-schema audit table.
   - Caveat: suite DBs are dense random DBs built for evaluation, not answer-preserving/changing per family, and they exist only for dev DBs, so this is audit- or eval-only.
2. **Generic operator module**, e.g. a new `sqlcf/generic_cf.py`. Introspect the schema with `PRAGMA table_info` / `foreign_key_list` and apply family-blind ops to the rows the gold query touches: duplicate child rows, add FK-closed clones (generalising `t_clone`), delete rows (generalising `_closure` with discovered FKs), NULL injection, tie creation and threshold shifts.
   - Classify each copy as preserving or changing against gold, as `build_items` already does.
   - This is the piece that enables training on Spider/BIRD train DBs.
3. **Second synthetic domain:** new `db.py`/`templates.py`/edits. Highest effort, lowest marginal credibility vs (1)–(2).

**New rewards need only `rewards.py` additions plus a CLI choice.** Candidates:
- C-penalty;
- strict-with-only-effective-copies: filter copies at build time by `kills(k) > 0`, a change in `_select` (L413–428);
- partial credit, already prototyped in `scripts/partial_credit.py`.

A `k_min` or "require kill" flag in `_select` would remove the inert copies found in Q3(d).

### Gaps
- Zhong suites are licensed Apache-2.0 per the earlier report, but whether suite DBs exist for Spider *train* DBs (needed for training rather than audit) was not checked in the repo. Only dev suites appear to be used.
- No estimate in the repo for BIRD DB sizes vs the 5 s / 100k-row sandbox limits.
